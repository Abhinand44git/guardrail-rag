# ADR-0026: Temporary passwords must be changed, expire, and a change signs out every other session

- **Status:** Accepted
- **Recorded:** 2026-10-28
- **Related:** ADR-0013, ADR-0016, ADR-0018, ADR-0021, ADR-0024. Migration `0014`. Closes review item #9 (Batch C).

## Context
Every account is created with a random password that is emailed. Until now that password was permanent (no way to change it, no expiry, nothing forcing the owner to replace it), and a password change would not have ended anyone's existing sessions: the token blacklist is per token id, so it cannot say "all of this person's tokens".

## Decision
- **Forced change at first login.** `users.must_change_password` (and the same flag on `operators`) is set whenever a temporary password is handed out: Operator creating a first Admin, Admin creating a user, Admin reissuing. Login still succeeds and returns `password_change_required: true`. While the flag is set, **every endpoint except `POST /auth/change-password` and `POST /auth/logout` returns 403 `password_change_required`** (operators: `/operator/change-password`, `/operator/logout`). The rule lives in `app/deps.py::require_user` / `require_operator`, the dependencies everything else is built on, so it is default-deny: a future endpoint cannot forget it.
- **`POST /auth/change-password`** takes the current and the new password. The current password is required even though the caller is logged in, so a left-open or stolen session is not enough to take over the account. On success: the new hash is stored, the flag is cleared, and a fresh token is returned.
- **A change signs out every other session.** `users.session_version` (and `operators.session_version`) is an integer; each token carries the version it was minted with (claim `sv`). A token is refused unless its `sv` equals the row's current value. A change or reissue bumps it. Considered and rejected: a per-token blacklist (cannot express "all of one person's tokens"); an issued-at timestamp (`iat` has one-second precision, so a token minted in the same second as the change is ambiguous). The counter is exact, race-free (bumped atomically in SQL), costs one integer on a row `require_user` already loads, and follows ADR-0024: the database is the authority, not the token. Tokens minted before this feature have no `sv` and count as version 0, so they keep working until the person's first change.
- **Policy** (`app/password_policy.py`): at least 12 characters; at most 72 bytes (bcrypt silently ignores bytes beyond 72, so a longer password would be accepted and then verify against only its first 72 bytes); different from the current password; must not contain the username or the part of the email before the `@` (when 3 or more characters); not in a small list of very common passwords; at least 5 different characters. No capital/digit/symbol composition rules (they hurt memorability without helping resistance; NIST SP 800-63B advises against them).
- **Temporary passwords expire.** `users.temp_password_expires_at` is set to now + `TEMP_PASSWORD_TTL_HOURS` (default 72). While the password is still temporary and past its expiry, login with the correct password is refused with a distinct "expired" message (distinct is safe: it is only reached after the password verified, same reasoning as the deactivated-account message). Once the person has set a real password nothing expires.
- **Admin reissue.** `POST /admin/users/{id}/reissue-password` (Admin only, not on yourself, not on a deactivated user, generic 404 for a missing or other-tenant id) generates a new temporary password, emails it (never in the response), marks it temporary, and signs the user out. It exists because expiry without a way back would lock people out for good. All-or-nothing, like account creation: if the email fails, nothing changes. It is the Admin-triggered minimum, not the self-service "forgot password" flow, which stays Phase 6.
- **Operator plane.** Same flag, same `sv`, mirror `POST /operator/change-password`. **`require_operator` now loads the operator's row on every request** (before, only the token was trusted), because the version and the flag live there; a token for an operator that does not exist is refused.
- **Existing accounts are untouched by the migration:** nobody is forced to change a password and no session is revoked. There is no way to tell which existing passwords were temporary, so a temporary password emailed before the upgrade stays valid until its owner changes it.

## Consequences
- Not built, named: no rate limit on `change-password` or login (a stolen token could guess the current password; Phase 6); no email telling a person their password was changed; no breached-password database check; no password history.
- The first Admin of every new tenant, and every user an Admin creates, now has a short first-login ceremony. That is intended, and the demo/seed accounts (not temporary) are unaffected.
- Two existing tests changed on purpose: the full-chain test now goes through the forced change, and an operator-logout test needed a real operator row.

## How this is checked
`tests/test_password_lifecycle.py` (54 tests, real Postgres): the **entire route table is walked** and every tenant and operator route except the exempt ones must refuse a pending-password account; the first-login flow end to end; other sessions die on a change and the caller's fresh token works, including a *later* login; wrong current password; each policy rule and its exact boundaries (12 characters, 72 bytes); forged tokens with older, newer or missing `sv`; expiry; reissue and its guards; every path that hands out a temporary password marks it; the operator plane; the policy as a pure function. `tests/test_migration_0014.py`: existing rows get safe defaults and keep their hashes; downgrade removes exactly the new columns. Mutation-checked: 26 deliberate breaks (removing either default-deny check, either session check, the version bump, the current-password check, the policy, each policy rule, the expiry, the reissue guards, the flags, the TTL setting, the version in either login) each fail a test; one gap found and closed along the way (an operator logging in after a change).
